# Logic, performance, and memory review — 2026-09-25

The primary agent and three independently scoped reviewers examined command/storage actions, process inspection/control, and UI/observation lifetimes. A separate reviewer then cross-checked the final controller and URL changes. Six reproducible P2 issues were fixed; no additional process-signalling or DOM-leak claim was established.

## Confirmed issues and repairs

| Issue | Trigger and previous result | Repair and regression |
| --- | --- | --- |
| A late refresh restores stale commands | Refresh reads old storage while a save/delete is pending; its reply overwrites the completed local mutation | Invalidate reads again after write completion; deterministic delayed set/delete tests |
| Terminal replies overwrite concurrent changes | Another panel renames, removes, forgets, or replaces an association while startup permission/response is pending | Reread storage; only update the same opening association and preserve current fields; success/failure cases plus lost storage acknowledgment |
| Independent listeners share history | Same directory/executable/port, different IPv4/IPv6 bindings | Include sorted endpoints in the history key; keep separate samples and avoid false replacement warnings |
| Sustained resource hints never appear at some cadences | A 5-second delay plus scan time yields 5.9- or 9-second samples; a fixed 35-second bin never spans the required 30 seconds | Select the nearest sample spanning at least 30 seconds from the latest recorded sample; retain minimum sample count, missing-reading and gap safeguards |
| Different bindings share a custom URL | Save the URL of one of two independent listeners on the same port | Include normalized endpoints in URL keys; only read a legacy key when its current match is unique |
| Concurrent URL saves lose one result | Two service forms clone the same old shared URL map before either write completes | Serialize map writes within a monitor and merge after the preceding write; failed writes do not block queued/later saves |

Production changes stay inside `Launchpad`, `ServiceMonitor`, and `ServiceHistory`; their caller interfaces, DOM strategy, scan interval, and process-control scripts remain unchanged. No runtime dependency, periodic reload, or speculative DOM cache was introduced. Storage has no atomic cross-window transaction: the new checks narrow stale windows, not eliminate that host limitation.

## Performance and memory

`npm run benchmark` before/after this pass, on the same machine:

| Fixture | Baseline median / p95 | Final median / p95 |
| --- | --- | --- |
| 20 services / 200 processes | 0.45 / 0.79 ms | 0.48 / 0.89 ms |
| 200 services / 6,000 processes | 9.59 / 12.52 ms | 10.15 / 13.32 ms |

These single paired runs do not establish a statistically reliable performance difference. Correct endpoint identity adds bounded sorting/serialization. Large-fixture retained JS heap after two forced-GC batches was 8,825,312 and 8,824,584 bytes. The distinct-scan memory regression retained **347,240 bytes (~0.33 MiB)** across 200 separate 6,000-process scans. These measurements cover synthetic Node/V8 data, not total Muxy or WebKit memory.

No new unbounded UI retention was confirmed. The earlier [WebKit attribution evidence](webkit-memory/attribution/README.md) still applies: an independent DOM-only workload reproduced a 1.36 GiB peak and naturally reclaimed memory in the same WebContent process. This pass does **not** claim to fix that peak or prove multi-day leak freedom. No further long soak was run because this patch changes bounded history/persistence logic, not detail DOM lifetime.
